# 泳道流程图规则

## 输入目标
将自然语言业务描述整理成适合泳道流程图的数据结构，核心是回答四件事：
- 谁在做
- 做什么
- 什么时候判断
- 产生什么文档、数据或外部交互

## 泳道规则
- 1 条泳道 = 1 个责任主体。
- 泳道名称可以写中文展示名，但 `id` 要稳定、简短、可复用。
- 不要把部门、岗位、系统混在同一条泳道里。
- 多角色协作时，拆成多个泳道，不要共用一个节点。

## 节点类型
- `start`：流程起点，只允许 1 个。
- `end`：流程终点，至少 1 个。
- `process`：普通动作，使用“动词 + 名词”的文案。
- `decision`：判断节点，必须能分出至少两个分支，常用“是 / 否”“通过 / 驳回”。
- `document`：表单、申请单、结果单、合同等文件。
- `database`：数据库、表、记录、状态等存储对象。
- `human`：必须由人工参与的操作。
- `input`：流程接收的外部输入。
- `output`：流程最终输出。
- `api`：外部系统接口调用。
- `subprocess`：复杂流程的子流程封装。

## 动作命名
- 使用“动词 + 名词”。
- 优先写业务动作，不写抽象描述。
- 示例：`提交报销申请`、`审核合同信息`、`调用支付接口`、`更新订单状态`。
- 避免：`报销申请`、`合同审核`、`支付` 这类过短或过于抽象的写法。

## 判断规则
- 判断节点必须有明确条件。
- 至少保留两个分支。
- 分支标签优先使用 `是 / 否`、`通过 / 驳回`、`通过 / 失败` 这类直观文案。
- 判断结果要继续流向后续动作，不要在判断节点处结束。

## 排版规则
- Start 放在左上角或最上方。
- 按流程顺序排列节点，尽量减少交叉线。
- 同层节点尽量保持对齐。
- 所有节点都要完整放在自己的泳道内。
- 连接线只画直线，避免曲线和回环。
- 节点文案尽量控制在一行内。

## flow.json 结构
```json
{
  "lanes": [
    { "id": "user", "name": "员工" },
    { "id": "system", "name": "业务系统" }
  ],
  "nodes": [
    { "id": "start", "text": "开始", "lane": "user", "type": "start" },
    { "id": "submit", "text": "提交申请", "lane": "user", "type": "process" }
  ],
  "edges": [
    { "source": "start", "target": "submit" }
  ]
}
```

## 生成时注意
- 先分析业务，再做结构化建模。
- 参考 `scripts/flow_demo.json` 的字段格式，不要照搬业务内容。
- 输出的 `flow.json` 要能被 `scripts/main.py` 直接读取。
- 生成结果默认写到 `scripts/output/flow.drawio`。
